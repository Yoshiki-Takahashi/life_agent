# Weekend 8以降: 段階的な強化

## Status / 共通方針

各枠の責務配置と既存サービスの拡張方法は[サービス設計・拡張指針](../service-design-guidelines.md)を参照する。方針は開発中に更新可能とし、変更時は本計画と契約も整合させる。

Planned。以下は実施順の枠であり、確定日程ではない。各枠の着手前に利用実績を確認し、その枠の詳細チケットと契約を作成する。条件付き機能は採用または見送り理由を記録し、採用した場合だけ実装・リソース作成する。

各枠のDoneは、下記の受け入れ条件、変更に対応するテスト・品質検査、AndroidまたはAPIでのデモ、契約・運用文書の更新、次回の最初の作業の記載とする。AI機能では読書・アプリ開発・筋トレの回帰評価を維持し、通常テストはFakeを使う。

## Weekend 8: 計画の見直し

**Sprint Goal / User Story:** ユーザーとして、実績に合わなくなった計画を、変更点を確認したうえで見直したい。

**受け入れ条件:**

- Re-plannerは既存計画と進捗から変更案だけを生成する。
- 現行計画との差分を表示し、承認時だけ更新する。取消・不正出力では変更しない。
- 提案後に計画が変更されていた場合は古い提案を適用しない。
- Metric変更後も過去のProgressLogを失わない参照・履歴方針を契約化する。

**対象外:** 無確認の自動再計画、複数Goal横断の優先順位調整。

## Weekend 9: 進捗の可視化

**Sprint Goal / User Story:** ユーザーとして、保存した実績から目標に近づいているかを把握したい。

**受け入れ条件:**

- Metric型に対応する推移グラフと目標値を表示する。
- 達成率の計算可能条件、未記録・目標値なしの表現を決め、根拠のない率を表示しない。
- 可視化タイプは許可済みの固定集合から選び、AIに任意の表示コードを生成させない。

**対象外:** 任意ダッシュボード作成、複数Goalの自動順位付け。

## Weekend 10: 定期振り返りと通知

**Sprint Goal / User Story:** ユーザーとして、希望する頻度で実績を振り返り、次の行動を確認したい。

**受け入れ条件:**

- 期間内の記録と助言を振り返り画面で確認できる。
- 通知の有効化・無効化、頻度、タイムゾーンを設定できる。
- 権限拒否時も手動で振り返れる。再実行による通知重複を防ぐ。
- 端末側の定期処理とサーバー定期処理を比較し、後者が必要な場合だけCloud Schedulerを導入する。

**対象外:** 無断通知、自動計画変更、複雑な配信最適化。

## Weekend 11: 音声による進捗入力

**Sprint Goal / User Story:** ユーザーとして、話した内容を修正・確認して進捗を記録したい。

**受け入れ条件:**

- 録音権限、開始・停止、文字起こし失敗を扱い、本文の編集・確認後にWeekend 7の経路へ渡す。
- 音声の送信先、保存有無、保持期間、削除方法を決めて画面と文書へ反映する。
- 音声保存が必要な場合だけCloud Storageを導入し、所有者分離と削除を検証する。

**対象外:** 常時録音、音声だけでの無確認保存。

## Weekend 12: 必要性に基づく基盤強化

**Sprint Goal / User Story:** 開発者として、遅いAI処理と環境の再構築を再現可能に扱いたい。

**受け入れ条件:**

- AI処理時間とタイムアウト実績を調べ、非同期化の採否を記録する。
- 採用する場合はCloud Tasks等の方式を選び、受付・状態確認・結果取得、再試行、二重反映防止を一つの利用経路で検証する。Pub/Subとの併用を前提にしない。
- 構成の安定性と複数環境の必要性を評価し、Terraform採用時は既存リソースの取り込み、state・秘密情報管理、破壊的差分の確認、再現手順を検証する。
- 不採用項目は再検討条件を記録する。AIサービスの分離も開発ガイドの基準で判断する。

**対象外:** 必要性のないサービス分割、未評価の本番リソース作成。

## Weekend 13: 認証方式の拡充

**Sprint Goal / User Story:** ユーザーとして、Googleアカウントでも既存のGoalへ安全にアクセスしたい。

**受け入れ条件:**

- Googleログイン、ログアウト、認証取消・失敗を扱う。
- 既存メール認証とのアカウント連携方針を決め、所有者IDと既存Goalへのアクセスを維持する。
- 電話番号認証は需要・SMS費用・不正利用対策を評価して採否を記録する。採用時は送信制限と所有者分離まで検証する。

**対象外:** 独自認証基盤、組織向けSSO。

## Weekend 14: 本番化判断と運用整備

**Sprint Goal / User Story:** 運用者として、利用規模と費用に合う公開範囲を決め、障害から復旧できる状態にしたい。

**受け入れ条件:**

- 公開要否、対象ユーザー、予算、データ保持・削除、可用性と復旧目標を定義する。公開しない場合は理由と再検討条件を記録する。
- 公開する場合は環境分離、権限、監視・通知、API利用制限、秘密情報更新、バックアップと復元を検証する。
- HA、read replica、独自domain、SLAは要件と費用から個別に採否を決める。
- リリース・ロールバック・障害対応手順と運用担当を定める。

**対象外:** 要件のないHAや常時稼働構成、予算通知だけを自動停止とみなす運用。
