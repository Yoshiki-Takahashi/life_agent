# サービス設計・拡張指針

## 位置づけと更新方針

この文書は、すべてのSprintで機能や責務の配置を判断する共通の参照元です。Codexを含む開発者は、計画・設計・実装の前に読み、既存サービスのどこを拡張するかを決めます。[ADR 0002](decisions/0002-ai-connection-boundary.md)のAI接続境界を基準とします。

開発中の発見や利用実績に応じて修正可能です。将来の構成を固定するものではありません。変更は理由と影響をPRに記載し、関連する契約・実装・設計文書・バックログを同じ変更で整合させ、Gitで履歴を管理します。サービス境界、DB所有権、認証・秘密情報の境界を変える重要な判断はADRにも記録します。既存のaccepted ADRを覆す場合は、新しいADRから旧判断との関係を明示します。日常的な配置の具体化に新規ADRは不要です。

文書の役割は次のとおりです。

- 本文書: 現在の配置原則と今後の拡張先。
- [システムアーキテクチャ](system-architecture.md): 現在のサービス構成、連携、セキュリティ境界。
- [ADR](decisions/README.md): 重要な判断の背景と理由。
- [開発ガイド](development-guide.md)・[バックログ](backlog/README.md): 実施順、機能範囲、受け入れ条件、完了状況。

相互に矛盾する場合は、最新の採用判断と実装を確認し、矛盾を解消してから進めます。将来の拡張方針を実装済みとは扱いません。

## 現在の責務配置

| 配置先 | 集約する責務 | 境界 |
| --- | --- | --- |
| Android (`android/`) | 入力、表示、候補の修正・確認、権限要求、画面状態、端末処理 | 業務通信はCore APIへ。Firebase認証はSDKで行う。AI秘密情報やDB接続を持たない |
| Core API (`backend/services/core-api/`) | 公開API、認証Token検証、所有者認可、正本の読取りと保存、業務検証、競合・重複反映防止 | アプリケーションDBの唯一の所有者。AIに渡すコンテキストを選び、生成結果を再検証する。OpenAI SDK・キー・プロンプトを持たない |
| Goal Planner / AI接続サービス (`backend/services/goal-planner/`) | AI Provider接続、キー、プロンプト、Structured Output生成、Providerエラー処理、Fakeと実AI評価 | ステートレスな内部サービス。初期計画・進捗解析候補・助言を生成する。アプリDB、ユーザー認可、正本更新を担わない |
| 契約 (`contracts/`) | 公開API・内部APIの入出力、固定Schema、エラーと更新の意味 | AI任せでSchemaを増やさない。AI側の生成制約とCore側の検証を契約に合わせる |
| 基盤 (`infra/`・`scripts/`・CI) | デプロイ、権限、Secret注入、監視、環境再現、運用手順 | 業務判断やAIプロンプトを配置しない。新規リソースは必要性と費用を評価して導入する |

Goal Plannerという現在のディレクトリ名・デプロイ名は維持し、内部AI接続サービスとして拡張します。初期計画だけに限定しません。正式な名称変更は、互換性と運用への影響を評価する別の変更とします。

Goal Planner、Progress Parser、Advisor、Re-plannerの「責務分離」は、機能ごとの契約・Provider・評価を独立して扱うことです。機能ごとの新しいCloud Runサービス作成は意味しません。Core APIには各機能の呼出し境界と業務検証を置き、実AI生成は既存のAI接続サービスへ寄せます。

## 新しい機能を追加する順序

1. ユーザーの入力から確認・保存・再表示までの経路を一つ決め、バックログに受け入れ条件を書く。
2. 画面・端末処理はAndroid、認可・正本・確定処理はCore API、AI生成はGoal Planner / AI接続サービスへ割り当てる。既存機能を再利用できるかを先に確認する。
3. 公開APIと内部APIの契約を先に決める。変更対象、所有者、エラー、確認の要否、競合・再送時の扱い、履歴保持を明示する。
4. Fakeで縦切りを完成させてから実AIを接続する。通常テストはFakeを使い、実AI評価は明示的に実行する。AI機能では読書・アプリ開発・筋トレの回帰評価を維持する。
5. 関連する品質検査、デモ、文書更新まで完了する。未採用の基盤は作成せず、条件付きの判断には採否・理由・再検討条件を残す。

AI呼出しに必要な正本はCore APIで所有者確認後に読み出し、必要最小限を渡します。AI応答待ちの間はDB transactionを保持しません。結果は候補として扱い、Core APIが構造と業務ルールを検証します。計画変更や進捗登録はユーザー確認後に短いtransactionで確定し、助言の失敗が保存済みの進捗を巻き戻さないようにします。

| Weekend 12: 非同期・基盤 | 非同期化が必要なら、Core側が受付・状態・結果と二重反映防止を管理し、AI接続サービスは生成を担当する境界を維持。Terraformはinfraへ配置 | 処理時間・timeout実績、queue方式とworker配置、再試行と結果確定の契約、既存リソース取込みとstate管理。Cloud TasksとPub/Subの併用や新規workerサービスを前提にしない |
| Weekend 13: 認証拡充 | Firebase AuthenticationとAndroidのログイン導線を拡張。Core APIは検証済みuidによる既存の所有者認可を維持 | メール認証とのアカウント連携、既存Goalの所有者維持。電話番号認証は需要・費用・不正利用対策から採否を判断 |
| Weekend 14: 本番化・運用 | infraと運用手順を中心に環境・権限・監視・復旧を整備。保持・削除やAPI利用制限の業務制御はCore側へ配置 | 公開要否、予算、運用担当、復旧目標。HA、read replica、独自domain等は要件と費用で個別判断 |

## 新しいサービスへ分離する条件

まず既存サービス内の小さな機能・呼出し境界として実装します。コード量や機能名だけを理由に、汎用フレームワーク、共有基盤、新しいデプロイ単位を追加しません。

次のいずれかが具体的に必要になったとき、独立サービス化を検討します。

- 他機能とは異なるスケーリング。
- 障害やtimeoutの隔離。
- 独立したリリース頻度。
- 個別の秘密情報・権限境界。
- 独立した性能・品質評価のための実行環境。

分離時は、既存サービス内で対応する案と比較し、効果と通信・運用コスト、契約互換性、データ所有権、移行・ロールバック方法をADRへ記録します。機能別のテストや評価だけで足りる場合はサービスを増やしません。契約テストを整えてから実行単位を移します。
