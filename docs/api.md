# APIの約束

業務APIは`Authorization: Bearer <Firebase ID Token>`を要求します。
メール認証とGoogle認証で同じFirebaseのuidを所有者として扱います。Google ID TokenはAndroidでFirebaseへ交換し、業務APIにはFirebase ID Tokenだけを送ります。
個人利用のクラウド環境では、検証済みTokenのuidが本人の`ALLOWED_USER_ID`または追加の`ALLOWED_USER_IDS`（カンマ区切り）に含まれる利用者だけを許可します。
追加許可された検証アカウントも、本人のGoalを参照・更新できません。
他のuidは、DB操作・AI呼出し前に403で拒否します。クライアントが送るメールアドレスやuidでは判定しません。
現在の正確なフィールドと型はCore APIの`/openapi.json`、内部通信の型は各サービスのPydanticモデルが正本です。
この文書では利用者に影響する規則を説明します。生成されたSchemaの写しは手編集しません。

## 入口

| 操作 | Core API | 保存 |
| --- | --- | --- |
| Goalを具体化する質問を作る | POST /api/v1/goals/questions | なし |
| 計画案を作る | POST /api/v1/goals/preview | なし |
| 計画を確定する | POST /api/v1/goals/confirm | 目標と計画 |
| 一覧を読む | GET /api/v1/goals | なし |
| 詳細を読む | GET /api/v1/goals/{id} | なし |
| 今回値を解析する | POST /api/v1/goals/{id}/progress/preview | なし |
| 実績を保存する | POST /api/v1/goals/{id}/progress | 種別に応じた値・完了状態と記録 |
| 助言を取得する | POST /api/v1/goals/{id}/advice | なし |
| 再計画案を作る | POST /api/v1/goals/{id}/replan/preview | 未適用の候補 |
| 再計画を適用する | POST /api/v1/goals/{id}/replan/apply | 承認した変更 |
| 全目標を相談する | POST /api/v1/coach/messages | なし |
| 改善メモを送信する | POST /api/v1/feedback | GitHub Issueと本文を含まない送信控え |

`GET /health`は認証不要の稼働確認です。
メンテナンス中は`/api/`以下に503と`Retry-After: 60`を返します。保存結果が不明な実績は、再開後も同じ保存IDで再送します。
内部AI APIは`/internal/v1/goal-questions`、`goal-plans`、`progress-preview`、`advice`、`replan`、`coach`です。
Androidから直接呼びません。

## 改善メモ

`POST /api/v1/feedback`は既存のFirebase認証・許可UID制限を適用します。
`client_request_id`（UUID）、`body`（前後空白除去後1〜2,000文字）、
`app_version`（改行なし1〜100文字）、`screen`（定義済み画面名）を受け取ります。
送信先リポジトリ・ラベルはサーバーが決め、利用者からは指定できません。
GitHubへ本文・サーバーの初回送信日時・アプリ版・画面名を渡し、
`feedback`と`needs-triage`を付けたIssueを作ります。AIは使いません。
成功時は200で`issue_number`と`issue_url`を返します。再送時も同じ結果です。

Firestoreの`feedback_receipts`には送信IDと所有者から作ったハッシュをキーに、
固定モデルで本文を含まない送信控え（payloadのSHA-256、リポジトリ、状態、初回日時、Issue番号）だけを保持します。
同じ所有者・送信IDの内容変更は409です。別の所有者とは控えを共有しません。
transactionで作成権を予約し、GitHub呼出しはtransaction外で一度だけ行います。
GitHubの作成が成功して控えの更新に失敗した場合も、再送でIssueを照会して復旧します。

GitHub認証未設定・明確な作成拒否は503で`detail.result_unknown=false`です。
切断・timeout・5xxなどの結果不明は同じIDで照会し、未確認なら503で
`detail.result_unknown=true`と`detail.message`を返します。GitHubの生エラーやTokenは返しません。
照会は初回日時の1秒前以降の全状態（closedを含む）をList APIで最大500件まで走査し、本文末尾の送信マーカーで照合します。
検索インデックスに依存せず、見つからないことを理由に作成を再実行しません。
作成前にサーバーが停止した場合も結果不明として残ります。手動で未作成を確認するまで自動再作成しません。

## 計画

タイトルは1〜120文字、説明は任意で2,000文字以内、期限は今日以降です。
`questions`はタイトル・説明・期限から、AIが選んだ3〜8問のYes / No質問を`questions: string[]`として返します。
各質問は1〜200文字、重複不可です。質問生成は既存のGoal Planner backend / provider設定を使用します。
`preview`は任意の`answers`配列（最大8件）を受け取ります。各要素は`question`（1〜200文字）と
`answer`（厳密なboolean）で、質問の重複やnull・文字列の回答は拒否します。
質問・回答は計画生成の文脈だけに使い、確定計画やDBへ保存しません。
既存クライアントの`answers`省略は空配列として扱います。新しいAndroidは全問回答後だけ提案へ進みます。

AIの初期提案は測定項目1〜3個、中間目標3〜5個です。
利用者が編集して確定する計画は、それぞれ1〜10個です。再計画の候補にも同じ許容件数を適用し、
件数制約を理由に追加項目を削らせません。中間目標の期限は今日からGoal期限までで、表示順に並びます。
数値目標は正数、小数2桁まで、最大10億です。
再計画の見直し理由は1〜2,000文字。累計型では現在値を下回る目標値へは変更できません。測定値型の目標は現在値より小さくても指定できます。
候補の適用には提案IDを使い、適用済み・古い計画版の候補は409で拒否します。

## 実績

本文は1〜2,000文字。`metric_updates`で既存Metricを1〜10件指定します。
同じMetricの重複、非表示・他目標のMetricを拒否します。数値は小数2桁まで、最大10億です。
記録の意味は下記の種別に従います。文章だけの実績は保存しません。
累計の今回値と加算後の現在値は目標値を超えても保存できます。明示した0も履歴に残し、全て0でも保存できます。
空欄は更新対象から省略し、文章だけの実績は保存しません。計画の目標値は引き続き正数です。
解析候補は0件でも返せます。その場合は理由を示し、修正・手入力を選べます。

`client_request_id`は1〜64文字。同じ保存操作の再試行では同じIDと内容を送ります。
同じIDによる保存は一回だけ反映します。新しい実績には新しいIDを使います。
助言の再取得は保存APIとは別です。
Firestoreへの変更後も公開JSON・UUID・順序・全履歴返却を維持します。内部の数値は整数で保存し、APIでは従来どおり小数として扱います。

## 全目標コーチ

入力は`body`（1〜2,000文字）と`history`（最大12発話）。発話はuserまたはassistantで、各本文は1〜2,000文字です。
返答は`reply`、`intent`（discuss / record）、`goal_id`、`record_body`です。
相談では対象と実績本文をnullとし、記録候補では所有Goal IDと利用者の現在・過去発話の原文を必須とします。
AIが生成した実績文や、不明なGoal IDは採用しません。このAPIだけでは実績を保存しません。

## 失敗

入力不正は422、未認証は401、利用を許可していないアカウントは403、他人・存在しないGoalは404、再計画の競合は409です。
AIの障害・不正出力は503。保存失敗は500で返し、途中までの加算だけを確定しません。
コーチで保存結果が不明な場合は内容を固定して再送し、助言障害では助言だけを再試行します。

## 目標の完了とアーカイブ

`POST /api/v1/goals/{id}/complete` は所有者が目標の完了を確定し、`status=completed` を保存して詳細を返します。
目標値への到達は要求しません。transactionで状態と更新日時を変更し、完了済みへの再送では更新しません。
存在しない・他人の目標は404です。計画・Metric・実績は保持し、GETで引き続き取得できます。
`GET /api/v1/goals?status=active|completed` で一覧を絞り込めます。省略時は既存クライアントとの互換性のため全状態を返します。
既存の所有者索引で取得後に状態を絞り込み、新規索引は要求しません。
完了済みへの新規実績保存・再計画生成／適用は409です。保存済み実績の同じIDによる再送は成功を返します。
コーチには進行中の目標だけを渡します。完了取消・削除・自動完了は提供しません。

## メトリクスの4種別（Issue #47）

`kind`は固定の `cumulative` / `occurrence` / `measurement` / `checklist` です。
作成時にAIが提案し、本人が確認画面で編集・確定します。保存済みの種別は変更しません。
旧形式の`kind`省略は累計型です。計画生成の`metric_types_enabled=true`を送る新アプリには4種類を提案し、
省略・falseの旧アプリには累計型だけを返します。チェック項目はチェックリスト型だけに指定します。

| 種別 | 計画 | 実績の`value`と追加フィールド | 現在値・表示 |
| --- | --- | --- | --- |
| 累計 `cumulative` | 正の目標値と単位 | 0以上の今回増分。目標超過も可 | 加算・累積グラフ |
| 実行日 `occurrence` | 整数の目標日数と単位 | `value=1`と`activity_date`（端末の暦日） | 実行日数を加算・月別カレンダー |
| 測定値 `measurement` | 正の目標値と単位 | 0以上の測定値そのもの。目標値を超えてもよい | 最新の保存値へ置換・測定値の折れ線 |
| チェックリスト `checklist` | 一意な`checklist_items`を1〜20個（各1〜120文字）、目標値は項目数 | 完了項目の全体を`completed_items`へ、`value`はその件数。保存前状態を`expected_completed_items`へ | 完了状態を置換・チェック項目一覧 |

累計以外の実績保存は既存Metricと一致する`kind`の明示が必須です。旧アプリによる異なる意味の保存は422で拒否します。
解析候補では実行日と保存前のチェック状態を省略でき、Androidが今日の日付・読取り済みの状態を付けて本人に確認します。
実行日型以外の`activity_date`、チェックリスト型以外のチェック状態は拒否します。
実行日はUTC基準で翌日を超える未来日を拒否します（端末の時差を許容）。Androidの入力は今日のみです。
同一Goal・Metric・暦日の実行を別IDで重ねると409です。同じ保存IDの再送は成功を返します。
チェック保存の前提状態が現行状態と違うと409で再読込を求めます。未言及の項目をAIが取り消すことはありません。

測定前の初期値0は測定事実ではありません。`last_recorded_at=null`で区別します。
測定値の増減の良し悪し・目標の方向は自動判定しません。履歴の`kind`と`activity_date`、
`completed_items`を返すため、チェックの取消や測定値0も履歴から確認できます。
再計画では既存の配列位置ごとの`kind`・`unit`・`checklist_items`を保持し、異なる意味への履歴の読み替えを拒否します。
