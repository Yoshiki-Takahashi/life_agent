# サービス設計の原則

機能の配置と責務の境界を判断する共通指針です。
現在の動作は[仕様の入口](README.md)、構成とデータは[システム](system-architecture.md)を参照してください。
AI接続の境界は[ADR 0002](decisions/0002-ai-connection-boundary.md)に従います。

## 責務の配置

| 配置先 | 集約する責務 | 境界 |
| --- | --- | --- |
| Android | 入力、表示、確認、画面状態、端末処理 | 業務通信はCoreへ。AI秘密情報とDB接続を持たない |
| Core API | 公開API、認証・所有者認可、正本データ、業務検証、transaction、重複・競合の防止 | DBの唯一の所有者。AIへ渡す情報を選び、候補を再検証する |
| Goal Planner / AI接続サービス | Provider接続、キー、プロンプト、Structured Output、生成失敗の扱い、Fakeと実AI評価 | ステートレス。アプリDB・公開API・利用者認可を持たない |
| contracts | API契約の入口 | 正確な型はPydanticとOpenAPIから生成し、コピーを手編集しない |
| infra / scripts | 環境、権限、デプロイ、起動・停止、検証補助 | 業務ルールを配置しない |

## 既存サービスの拡張

- まず責務に合う既存の機能ファイルを拡張する。AI機能ごとにデプロイ単位を増やさない。
- 初期計画、進捗解析、助言、再計画、全目標対話の生成は既存の内部AIサービスへ集約する。
- AIを待つ前にDBの読取りtransactionを閉じる。生成結果は本人の確認前に正本へ反映しない。
- 再送と競合はCoreで制御し、使わなくなったMetricも履歴から参照できるように残す。
- FirestoreでもDBの所有者はCoreだけとする。現在値と履歴は原子的に保存し、再試行されるtransaction内でAIや外部処理を呼ばない。[ADR 0003](decisions/0003-firestore-standard.md)に従い、固定の保存モデルを維持する。
- 表示・入力・状態処理は機能単位でまとめ、通信とOS処理の境界は維持する。
- 改善メモのGitHub連携はCoreの`feedback.py`へ配置する。本文の正本はGitHub Issuesとし、
  Firestoreには本文を含まない送信控えだけを保存する。GitHub TokenはCoreだけが保持し、AI接続サービスを経由しない。
- 共通化は実際の重複に限る。将来の汎用フレームワークや不要な階層を追加しない。

## 新しいサービスへ分離する条件

独立したスケーリング、障害隔離、リリース頻度、権限、性能・評価環境が具体的に必要な場合だけ検討する。
コード量や機能名だけを理由に分離しない。通信・運用コストと既存サービス内で対応する案を比較する。

配置や契約を変えたら現行仕様も更新する。サービス境界、DB所有権、認証・秘密情報の境界を変える判断はADRへ記録する。
通常のファイル統合や既存責務内の整理に、新しいADRやサービス層は追加しない。
