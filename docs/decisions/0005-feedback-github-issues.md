# ADR 0005: 改善メモをGitHub Issuesへ送信する

- 日付: 2026-11-07
- 状態: accepted
- 管理: [Issue #34](https://github.com/Yoshiki-Takahashi/life_agent/issues/34)

## 背景

利用者は開発者1人。利用中の改善点を素早く記録し、次の開発開始時に既存のIssue中心の開発へ接続したい。
アプリDBだけのメモ保管では転記が必要になり、Markdownへの追記は送信ごとのコード変更になる。

## 決定

Androidの下部メニューにフィードバック画面を置き、認証済みCore APIからGitHub Issueを作成する。
本文・整理・対応状況はGitHubを正本とし、AIによる整形や新サービスは追加しない。
GitHubの対象リポジトリ限定・Issues書込み権限のTokenをCoreだけが持つ。
Androidは送信先・自動添付する情報を表示し、本文・送信IDを保持する。

## 再送と保存

GitHub Issue作成とFirestoreを原子的にcommitできないため、Firestoreには本文なしの送信控えを保持する。
所有者とUUIDから文書IDを作り、payloadハッシュ・送信先・状態・初回日時・Issue番号を固定モデルで保存する。
transactionで一つの作成権を予約し、transactionの外で一度だけGitHubを呼ぶ。
同じID・異なる内容を拒否し、成功済みの再送は同じIssue番号を返す。

通信切断、5xx、作成後のFirestore更新失敗は結果不明として扱う。
同じIDの再送ではclosedも含めたList APIと本文末尾のマーカーで照合し、見つかれば控えを完了にする。
一覧走査には上限を設け、未検出でも作成を再実行しない。
明確な作成拒否だけを再試行可能に戻す。外部サービスをFirestore transaction内から呼ばない。

## 影響

メモ本文の二重管理を避けながら、並行送信・応答消失・Core再起動後も重複作成を防止できる。
予約直後・GitHub送信前にCoreが停止した場合は、未作成でも自動再作成できない。
この場合はGitHubの未作成と処理停止を開発者が確認した後、控えを再試行可能へ戻す。
単独利用の現段階では、自動配送基盤や定期Jobを追加せず、この制約を受け入れる。
送信控えは再送防止のため自動削除しない。将来の削除はクライアントの再送可能期間と合わせて設計する。

GitHub接続未設定でも既存機能は利用でき、フィードバック送信だけが再試行可能な設定エラーになる。
開発開始時に`feedback`かつ`needs-triage`のIssueを確認して、開発対象を具体化する。
